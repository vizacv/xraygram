# Xraygram macOS — отчёт о тестировании

Дата: 2026-11-18. Тема тестирования. План и ID проверок: [plan.md](plan.md). Ручные проверки: [macos-manual.md](macos-manual.md).

**Что тестировали:** `upstream/xraygram-local/dist/Xraygram.app` (tdesktop 7.4.4 = 7004004, Release, ad-hoc подпись,
bundle id `io.github.xraygram.desktop`), `xraygram-core` с xray 26.11.9. MacBook Air M5 (Mac17,3), macOS 26.7.1 (25G241),
выход в сеть по кабелю (USB LAN), все VPN выключены.

**Экземпляры:**
- основной Xraygram владельца (данные в `~/Library/Application Support/Xraygram`, вошёл в аккаунт, одна XRAY-запись):
  только наблюдение (`ps`, `lsof`, `nettop`, чтение лога), процессы не трогал;
- отдельный тестовый: `build-local.sh run` с `XRAYGRAM_APPDATA=upstream/xraygram-local/appdata-qa`. Туда скопированы
  только `tdata/settingss` и `tdata/xraygram.json` владельца (список прокси и ссылка, без аккаунта: экран входа).
  После тестов папка удалена.
- сам `xraygram-core` отдельно, с фиктивной ссылкой на `192.0.2.1`.

Адрес VPS ниже заменён на `<VPS>`, локальный IP — на `<LAN>`. Ссылки и пароли нигде не печатались.

## Итог в двух словах

- **Сообщения через xray работают, утечек в простое нет.** За 2 минуты наблюдения Телега ходила только на
  `127.0.0.1:<порт core>`, core — только на `<VPS>:443`. UDP-сокетов у Телеги нет.
- **Жизненный цикл core надёжный:** перезапуск после падения, backoff, смена занятого порта, выход вместе с приложением
  (Cmd+Q и `kill -9`). Пока core лежит, Телега напрямую не ходит.
- **Система не тронута:** системного прокси, TUN/VPN, LaunchAgents и фоновых объектов нет; после Cmd+Q ни процессов,
  ни портов.
- **Звонки через xray не идут и в текущем виде не могут** (MAC-01, MAC-02): в tdesktop 7.4.4 прокси для звонков
  выключен в коде, а у современных версий протокола SOCKS5 вообще не используется. Нужен патч tgcalls.
- **Мини-приложения (WebView) по коду идут мимо xray** (MAC-03), руками не проверено.
- Ещё по коду: удаление активной записи переключает Телегу на прямое соединение (MAC-04), первый запуск до добавления
  XRAY идёт напрямую (MAC-05).

## Баги и замечания

Нумерация для передачи Mac-теме. Важность: **высокая** (не работает ключевая функция или утечка без действий
пользователя), **средняя** (утечка или поломка в отдельном сценарии), **низкая** (неудобство, мелочь).

### MAC-01 — высокая. Звонки 1:1 всегда идут напрямую, мимо xray

Проверено по коду, руками ещё нет (CALL-02/03 в ручном сценарии).

1. `Telegram/SourceFiles/mtproto/mtproto_proxy_data.cpp:504`: `ProxyData::supportsCalls()` возвращает
   `false; // (type == Type::Socks5)`, то есть upstream выключил прокси для звонков целиком. Поэтому в
   `calls/calls_call.cpp:1242–1253` `descriptor.proxy` не заполняется никогда, независимо от настроек.
2. Галки «Use proxy for calls» в интерфейсе нет: `setUseProxyForCalls` вызывается только при чтении старых настроек
   (`storage/details/storage_settings_scheme.cpp:593`), в `boxes/connection_box.cpp` её нет.
3. Даже если включить п. 1: tdesktop регистрирует `InstanceImpl` (версии 2.7.7, 5.0.0), `InstanceV2Impl` (7–9, 12, 13)
   и `InstanceV2ReferenceImpl` (10, 11) (`calls_call.cpp:73–75`) и отдаёт весь список в `phone.requestCall`
   (`CollectVersionsForApi`). С современными клиентами, судя по номерам версий, согласуется v2 (какая именно — видно в
   `DebugLogs/last_call_log.txt` при включённом debug-логе). SOCKS5 в tgcalls подключает только старый
   `NetworkManager.cpp:143–149` (`set_proxy`, `PROXY_SOCKS5`). В v2 (`v2/NativeNetworkingImpl.cpp:596–602`) прокси лишь
   выключает UDP и STUN, а TCP до серверов-ретрансляторов идёт **напрямую**: `set_proxy` в v2 нет.
4. UDP в inbound (`udp:false` в `macos/core/main.go`) для этого пути не нужен: libwebrtc через SOCKS5 умеет только TCP
   (UDP ASSOCIATE не использует). Включение `udp:true` само по себе ничего не изменит.

Ожидаемое поведение сейчас: звонок открывает UDP-сокеты в процессе Телеги и идёт к серверам Telegram или к собеседнику
напрямую. Из РФ он может не соединиться или идти без звука.

Что нужно, чтобы звонки шли через xray (для Mac-темы):
- `supportsCalls()` → `true` хотя бы для XRAY-записей (`Xraygram::IsXrayProxy`) и всегда передавать их в `descriptor.proxy`
  (галка не нужна, или вернуть её);
- в tgcalls v2 (`NativeNetworkingImpl`, и в `InstanceV2ReferenceImpl`, если он строит сеть сам) при `_proxy` вызывать
  `_portAllocator->set_proxy(...)` с SOCKS5, как в `NetworkManager.cpp`, чтобы TCP-кандидаты (TURN/reflector по TCP) шли
  через 127.0.0.1;
- проверить, что Telegram отдаёт TCP-ретрансляторы (`phoneConnection` с флагом `tcp`) и что звонок поднимается
  только на TCP-relay (P2P и UDP выключены).
- tgcalls — сабмодуль, `update-patch.sh` правки в сабмодулях не выгружает (предупреждает). Нужен отдельный патч.

Шаги воспроизведения: macos-manual.md, раздел 2.

### MAC-02 — высокая. Групповые звонки, видеочаты и конференции идут напрямую

По коду: в `calls/group/*.cpp` нет ни одного обращения к прокси. Групповой движок tgcalls (`GroupInstanceCustomImpl`)
ходит к SFU Телеги по UDP/ICE напрямую. Исправление сложнее, чем для MAC-01: нужен TCP-транспорт через SOCKS5 в
групповом движке. Возможно, проще принять как ограничение и показывать предупреждение. Шаги: macos-manual.md, раздел 2, п. 5.

### MAC-03 — средняя. Мини-приложения ботов (WebView) по коду идут мимо xray

По коду: `lib_webview/webview/platform/mac/webview_mac.mm` не настраивает прокси для `WKWebView`. Прокси Телеги
применяется к своим соединениям и к Qt (`QNetworkProxy::setApplicationProxy`, `core/sandbox.cpp:715–729`), но WebKit
ходит через свой процесс `com.apple.WebKit.Networking` и системные настройки. Значит, Web App ботов, оплата и прочие
веб-страницы внутри клиента грузятся напрямую. Руками не проверено (LEAK-05; `net-watch.sh` отметит их как `WEBVIEW`).
Исправление: на macOS 14+ `WKWebsiteDataStore.proxyConfigurations` с
`nw_proxy_config_create_socksv5(127.0.0.1:<порт>)` + `nw_proxy_config_set_username_and_password` для активной
XRAY-записи. Если это сложно, можно предупреждать пользователя или не открывать WebView без прокси.
Шаги: macos-manual.md, раздел 6.

### MAC-04 — средняя. Удаление активной XRAY-записи сразу переключает Телегу на прямое соединение

По коду (поведение upstream): `boxes/connection_box.cpp:2831–2839`. Если удалить выбранный прокси, настройки становятся
`ProxyData::Settings::System`, а без системного прокси это прямое соединение с серверами Telegram. Ровно так же
действует «Отключить прокси». Для обхода блокировок это тихая утечка: пользователь мог просто чистить список.
Предложение: если удаляется активная XRAY-запись, переключаться на другую XRAY-запись, а без неё — `Disabled` с
подтверждением («Телега пойдёт напрямую, продолжить?»). Отдельной задачей — режим «никогда не ходить напрямую»
(kill switch). Шаги: macos-manual.md, раздел 3, п. 6.

### MAC-05 — низкая/средняя. Первый запуск до добавления XRAY идёт напрямую

В логе владельца приложение запущено в 14:28:09, а `Xraygram: xray started` появилось в 14:29:09. Всю минуту до этого
прокси не было, и по коду Телега подключалась к DC напрямую (экран входа или уже вошедший аккаунт). Так ведёт себя любой
клиент Telegram, но для нашей аудитории первое прямое подключение уже сигнал для провайдера. Предложение: при первом
запуске без записей сразу открывать окно «Ссылка XRAY» и не подключаться до её ввода (или до явного «без прокси»).

### MAC-06 — низкая. Удалённая XRAY-запись: core и ссылка живут до перезапуска

По коду: в `xraygram/xraygram_core.cpp` у `Manager` нет удаления: `connection_box.cpp` при удалении записи ничего не
сообщает в `Xraygram::`. Процесс `xraygram-core` удалённой записи работает дальше, держит порт, а ссылка с ключом
остаётся в `tdata/xraygram.json` до следующего запуска (тогда `Manager::start` её выбросит). Если запись удалили и
сразу восстановили, всё правильно, поэтому останавливать core лучше при закрытии окна прокси или при сохранении
настроек. Шаги: macos-manual.md, раздел 3, п. 5.

### MAC-07 — низкая. После нескольких падений core связи нет до 2 минут, и пользователю не видно почему

Проверено (CORE-02): backoff 3 → 6 → 12 → 24 → 48 с (до 120). Это по дизайну. Но в интерфейсе виден только общий статус
«Подключение…», а `lastError()` экземпляра нигде не показывается. Предложение: в списке прокси под XRAY-записью писать
«xray перезапускается через N с: <ошибка>», а кнопкой «подключить» сбрасывать backoff.

### MAC-08 — низкая. Тексты ошибок ссылки сырые, на английском

`xraygram-core check` отдаёт `ERROR unsupported share format`, `no valid outbound found`, `empty link`, и окно
показывает их как есть. `vless://` без `encryption=none` или Reality без `pbk` тоже дают «no valid outbound found».
Предложение: перевести 3–4 частые ошибки на русский («это не ссылка vless/vmess/trojan/ss/hy2», «в ссылке не хватает
параметров: …»).

### MAC-09 — низкая (процесс). Тестовый экземпляр не отличить от основного

`build-local.sh run` запускает тот же бандл: то же имя «Xraygram», та же иконка и тот же bundle id. Окно тестового
экземпляра выскакивает поверх и забирает фокус клавиатуры. Во время тестов владелец печатал в основном окне,
появилось тестовое, туда ушли 3 нажатия, а потом владелец закрыл оба (Cmd+Q в 14:44:22 и 14:44:24, видно в системном
журнале). Предложение для `run`/`run-dev`: заголовок «Xraygram (test)» или другой bundle id/иконка, запуск без активации
окна (`open -g`). До исправления разрушающие тесты на тестовом экземпляре согласовываю с владельцем заранее.

### Замечания без номера

- **Хвост лога xray в `log.txt`.** При падении core в обычный лог пишется до 4 КБ его вывода, включая access-строки
  вида `from tcp:127.0.0.1:… accepted tcp:149.154.167.50:443`. Секретов там нет, только адреса назначения.
- **Зависший core не обнаруживается** (CORE-04): пока core остановлен, связи нет, после `SIGCONT` она возвращается через
  1 с. С мёртвым VPS будет так же: проверки здоровья нет, только перезапуск при выходе процесса. По дизайну, не баг.
- **IPv6 до DC.** Телега через SOCKS просит и IPv6-адреса DC (`[2001:67c:4e8:f002::a]:443` в логе core). Если у VPS нет
  IPv6, это лишние неудачные попытки. Влияет только на скорость подключения.
- **Пароль SOCKS** передаётся core через переменную окружения: другие процессы того же пользователя могут его видеть
  (`ps -E`). Им и `xraygram.json` доступен, так что новой поверхности атаки нет.

## Что проверено и как

### LEAK-01, LEAK-03 — простой основного экземпляра: только 127.0.0.1 ✅

Сэмплинг `lsof -nP -a -p <pid> -i` раз в секунду, 120 с, по Телеге (pid 22626) и её core (pid 22730),
разовым скриптом (то же теперь делает `testing/scripts/net-watch.sh`), затем свёрнут по уникальным парам:

```
120 22730 xraygram- TCP <LAN>:*-><VPS>:443 (ESTABLISHED)
120 22730 xraygram- TCP 127.0.0.1:51619 (LISTEN)
120 22730 xraygram- TCP 127.0.0.1:51619->127.0.0.1:* (ESTABLISHED)
120 22626 Telegram  TCP 127.0.0.1:*->127.0.0.1:51619 (ESTABLISHED)
```

Хост из `summary` в `xraygram.json` (без ссылки и пароля) совпадает с адресом, куда ходит core. UDP-сокетов нет.
Ограничение: это простой, без загрузки медиа. Под нагрузкой — LEAK-02, руками с `net-watch.sh`.
Тестовый экземпляр на экране входа дал то же: `Telegram → 127.0.0.1:51813`, core → `<VPS>:443`.

### LEAK-04 — DoH и прочие обходы по коду ✅ (нет при SOCKS)

- `SpecialConfigRequest` (DoH к `dns.google.com`, `mozilla.cloudflare-dns.com`, Firebase, `NoProxy`) для конфига не
  создаётся при включённом прокси: `mtproto/config_loader.cpp:118–122` (`if (_proxyEnabled ...) reset`).
- `syncHttpUnixtime` (тот же DoH для времени) вызывается только из `details/mtproto_tls_socket.cpp` (фейк-TLS MTProto-прокси),
  у SOCKS5 этого пути нет.
- `DomainResolver` (DoH) нужен только для прокси с именем хоста (`tryCustomResolve`), у нас `127.0.0.1`.
- Прочий HTTP Qt (`WebFileLoader` и т.п.) идёт через `QNetworkProxy::setApplicationProxy` = наш SOCKS (`core/sandbox.cpp:721–724`).

### LEAK-07 — пока core лежит, Телега не ходит напрямую ✅

`kill -9` core тестового экземпляра (пятое падение подряд, пауза 41 с), опрос `lsof` Телеги каждые 0,25 с: ни одного
сокета за всё время. Прокси не отключается и на прямое соединение не переходит.

### EXIT — выход ✅

- EXIT-01, тестовый экземпляр: штатный выход через `NSRunningApplication.terminate` (тот же Apple Event «quit», что
  Cmd+Q и «Завершить» в Dock), адресно по PID. Приложение вышло за 0,1–0,2 с, core исчез, порт свободен.
- EXIT-01, основной экземпляр: владелец сам нажал Cmd+Q в 14:44:22 (системный журнал: `Telegram[22626] terminate:`;
  в логе Телеги `Api::Updates prevents quit, sending offline status...`). После этого нет ни Телеги, ни core 22730,
  порт 51619 свободен.
- EXIT-02: тестовый экземпляр закрыт Cmd+Q, когда его core был остановлен (`SIGSTOP`). Приложение вышло за ~2,8 с
  (`terminate` → 2 с ожидания → `kill`), core убит, ничего не осталось.

### SYS — влияние на систему ✅

`testing/scripts/sys-check.sh` при запущенном основном Xraygram и после выхода всех экземпляров дал одно и то же:

- `scutil --proxy`: только `ExceptionsList` и `FTPPassive`, прокси нет. `networksetup`: у всех 12 служб `socks/web/secure/pac=No`.
- Туннели: `utun0..utun3` и при запущенном Xraygram, и без него (системные). VPN-конфигурации — только чужие (WireGuard,
  V2Box, FortiClient), все `Disconnected`.
- LaunchAgents/Daemons с xray нет. `launchctl` — только стандартная GUI-запись `application.io.github.xraygram.desktop.*`,
  её создаёт сама macOS для любого запущенного приложения. `sfltool dumpbtm`: 0 упоминаний xraygram (автозапуска нет).
- В бандле нет `Contents/Library` (LoginItems/LaunchServices), entitlements пустые (ad-hoc, без Network Extension).
- После выхода: процессов и слушающих портов Xraygram/xraygram-core нет.
- Следы вне папки данных: `~/Library/Preferences/io.github.xraygram.desktop.plist` (обычные настройки macOS), пустой
  `~/Library/Application Support/Xraygram` при запуске с `-workdir` (уже описано Mac-темой).
- `tdata/xraygram.json`: `-rw-------` (0600).

## Осталось проверить руками

Всё в [macos-manual.md](macos-manual.md) (~40 мин, для звонков нужен второй человек):

- MSG, MED, VOI под нагрузкой с `net-watch.sh` (LEAK-02);
- **CALL-02…06**: подтвердить MAC-01/02 и узнать, проходят ли прямые звонки у владельца;
- ENT-01…06: несколько записей, переключение, редактирование, удаление (MAC-04, MAC-06);
- LNK-02/03: ссылка с неверным ключом и недоступный сервер (не уходит ли Телега напрямую, что показывает статус);
- SLP-01, NET-01/02: сон и смена сети;
- LEAK-05: мини-приложения (MAC-03);
- CON-03: вход в аккаунт с нуля через XRAY (владелец входил, но, судя по логу, ещё до добавления XRAY: MAC-05).

Автоматически не проверено и требует отдельного решения: DNS-запросы процесса Телеги через системный резолвер
(видно только с правами root: `sudo log config` для mDNSResponder или `tcpdump`). По коду имён Телега при SOCKS не
резолвит, кроме WebView (MAC-03).

## Инструменты (переиспользуемые)
