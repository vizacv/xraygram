# План тестирования Xraygram

Общий чек-лист для всех платформ (macOS, Android, iOS). У каждой проверки есть ID, его упоминают в отчётах
(`testing/<платформа>-report.md`) и в ручных сценариях (`testing/<платформа>-manual.md`).

**Кто проверяет:** А = автоматически (тема тестирования, без рук владельца), Р = руками владельца,
К = по коду (вывод из исходников, требует подтверждения руками).

**Главный инвариант.** Когда выбрана XRAY-запись и прокси включён, процесс клиента ходит в сеть только на
`127.0.0.1:<порт xraygram-core>`. Наружу ходит только `xraygram-core` и только на VPS. Всё остальное считается
утечкой (раздел LEAK), кроме того, что пользователь включил сам (другой тип прокси, «без прокси»).

Инструменты для macOS: `testing/scripts/net-watch.sh` (сеть клиента и core), `testing/scripts/sys-check.sh`
(влияние на систему). На Android: `adb shell` + `/proc/net/tcp*`, `dumpsys connectivity`, `ss` у процесса. На iOS:
`nettop`/`rvictl` с Mac, Console. Свои скрипты для них — когда дойдём.

## CON — подключение

| ID | Проверка | Ожидается | Кто |
|---|---|---|---|
| CON-01 | Добавить XRAY-запись по рабочей ссылке (вставка, автоподстановка из буфера) | строка «Сервер: vless · host · имя», Save → «подключено» | Р |
| CON-02 | Холодный старт с сохранённой записью | core стартует сам, подключение без действий пользователя, < 10 с | А/Р |
| CON-03 | Вход в аккаунт через XRAY (экран входа → прокси) | код приходит, вход проходит | Р |
| CON-04 | Пинг XRAY-записи в списке прокси | число мс, не «недоступен» | Р |
| CON-05 | Первый запуск без записей | что делает клиент до добавления XRAY (ходит напрямую?) | А/К |

## CORE — падение и перезапуск ядра

| ID | Проверка | Ожидается | Кто |
|---|---|---|---|
| CORE-01 | `kill -9` core | перезапуск ≈ 3 с на том же порту, связь восстанавливается | А |
| CORE-02 | Несколько падений подряд | backoff 3 → 6 → 12 → … ≤ 120 с; клиент в это время не ходит напрямую | А |
| CORE-03 | Порт записи занят при старте | core на новом порту, запись в настройках переписана, связь есть | А |
| CORE-04 | Core завис (`kill -STOP`) | клиент не падает; после `-CONT` связь возвращается | А |
| CORE-05 | Смерть клиента (`kill -9`) | core сам выходит ≤ 1–2 с, порт свободен | А |
| CORE-06 | SOCKS-порт core: без пароля / неверный пароль / UDP ASSOCIATE | отказ / отказ / по текущему дизайну отказ (`udp:false`) | А |
| CORE-07 | Ссылка не видна в `ps` | в аргументах только `run -listen 127.0.0.1:PORT` | А |

## LEAK — утечки (Telegram мимо xray при включённом XRAY)

| ID | Проверка | Ожидается | Кто |
|---|---|---|---|
| LEAK-01 | Простой: соединения клиента в течение ≥ 2 мин | только 127.0.0.1 | А |
| LEAK-02 | Под нагрузкой: медиа, каналы, стикеры, поиск | только 127.0.0.1 | Р + net-watch |
| LEAK-03 | UDP-сокеты клиента вне звонков | нет | А |
| LEAK-04 | DNS: клиент не резолвит имена Телеги сам (DoH-фолбэки, `dns.google`, `firebase`) | по коду не должен при SOCKS-прокси | К |
| LEAK-05 | Встроенный браузер / мини-приложения (WebView) | идут ли через xray | К + Р + net-watch |
| LEAK-06 | Звонки (см. CALL) | идут ли через xray | К + Р |
| LEAK-07 | Пока core перезапускается или упал | клиент не ходит напрямую | А |

## Порядок прогона на новой платформе

1. А-проверки: CORE, SYS, LEAK-01/03/07/08, EXIT-01/02 на отдельном тестовом экземпляре или с отдельными данными.
2. К-проверки: CALL-01, LEAK-04/05 по исходникам этой платформы (код звонков и WebView у каждой платформы свой).
3. Ручной сценарий для владельца: CON, MSG, MED, VOI, CALL, ENT, LNK-02/03, SLP, NET с запущенным наблюдением за сетью.
4. Отчёт `<платформа>-report.md`: что проверено и как, баги с номерами `<PLT>-NN`, что осталось.

Правила: секреты (ссылки, пароль SOCKS, api_hash) и адрес VPS в отчёты не попадают (`<VPS>`). Открытый у владельца
клиент без его согласия не трогаем. Разрушающие тесты — только на отдельном экземпляре, и владельца предупреждаем
заранее: окно тестового экземпляра может перехватить фокус, пока он печатает.
